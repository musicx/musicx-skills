# 要查资料才能写的技术文章

发布解读、论文和模型分析、工具与方案对比、技术选型调研、趋势判断读这一份，和体裁参考（`longform.md` 或 `report.md`）一起读。它管成文之前的事：材料从哪来、能撑住什么说法、数字怎么比。只做文字校对时不用读。

## 先有问题，后有主线

- 先写清这篇对哪个读者的哪个具体问题有帮助。模型发布问的是"它让哪一项任务发生了可以验证的变化"，工具体验问的是"在什么工作流里省了什么、又多了什么成本"。
- 研究开始时，主线可以只是一个待回答的问题或一个暂定的判断。读完材料再定。遇到反证先改主线，不为保住主线筛掉反证。
- 围绕要发表的主张找资料。不必为一个题目收集一整套材料。

## 每种来源能撑住什么

| 来源 | 能支撑 | 不能自动支撑 |
|---|---|---|
| 官方发布、产品文档、定价页、模型卡 | 厂商公布的能力、版本、价格、可用范围 | 独立验证过的效果；所有用户的实际收益 |
| 论文、评测报告 | 这个实验在所述条件下的结果 | 已被独立复现；超出实验范围的结论 |
| 开源代码、可复现的实验、日志 | 实现细节、运行条件、实测结果 | 没测过的环境和任务 |
| 社区讨论（HN、Reddit、X、issue 区） | 某个用户提出的问题、观点或自述 | 多数用户的态度；核实过的事故 |
| 二手报道、转述、只读到的标题和摘要 | 有人这样报道了；去哪找原文 | 原文写了什么 |
| 作者自己的材料 | 作者实际做过的事、取舍和判断 | 材料之外的动机、场景和数字 |

- **同一个发布被多处转载和讨论，仍然只是一个来源。** 不把转载的数量当作旁证。
- **读到哪算哪。** 只读了标题、只读了摘要、读了全文，在笔记里分开记。读取失败时，缩小这条资料支撑的说法；要用正文里的具体内容却没读到，列为待核实。
- **这一轮确实读过并记下出处的资料，就是素材。** 不凭记忆补来源，不让标题或摘要去支撑没读过的正文。
- **关键主张在工作笔记里留五样：** 主张、出处、来源类型、读到的范围、时间和版本。简单的文章用短注就够，不必交一张大表。

## 数字和比较

会改变结论的性能或成本比较，保留能解释差异的那些条件。不必机械地把所有属性列齐。

- **比的是什么：** 名称、具体版本、日期。托管服务和本地部署分开说。
- **在什么任务上比：** 数据集和它的版本，指标，样本量，跑了几次。知道误差范围时保留。
- **条件是否一致：** 硬件、配置、并发、输入规模。比模型时还有提示词、工具、检索和推理预算；单轮和多轮分开，自动通过率和人工偏好分开。
- **成本怎么算的：** 计费项（输入、输出、缓存）、调用量、币种、计费日期。
- **"开源""免费""可用"说清范围：** 代码还是权重，什么许可证，能不能商用；演示可用不等于普遍可用。
- **条件不可比时，各写各的结果和边界，不凑一个统一排名。** 测试集、口径中途变了的，在数字旁边写明前后不可比。
- **说清指标衡量什么、不衡量什么。** 没有比较、没有测的部分，写明没做以及原因。
- **推算出来的数写明推算方法**（"按另一家的费率估算"），不和实测的数混在一列。
- **厂商图表里的数字归厂商。** 没有自己复现的，不写成实测。
- **一个跑分的变化不直接写成岗位或行业的结论。** 先说明它影响哪一类具体任务。

自己做实验和复现时再加三条：

- 每加一项改动报一次数，并跑一组只改这一项的对照，读者才知道提升来自哪一项。
- 先用最低线排除不达标的方案，再在剩下的里面比成本。
- 复现对不上时，逐条列出可能的原因，标明哪些已经排除、哪些还存疑。自己接触到的是哪一层证据也写明：亲手跑的、看过原始数据的，还是只看到别人的报告。

## 评论和反例

- 先看这条评论反对的是哪一句话，再提炼它提出的、可以核实的问题。
- 用户自述的失败写成"某用户称在某条件下失败"。找到日志或复现之后，才能把话说得更重。
- 攻击、玩笑、单纯的赞同和重复的论点不算技术证据。
- 没有真实的反证，不硬加一节"反方观点"。有真实的反例，就让它缩小或推翻暂定的主线。
- 社区记录里也有虚构内容、玩笑和模型输出，不把它们转写成已经发生的事。

## 成稿时

- 结构由读者的问题决定。不把研究笔记的字段逐个变成小标题。
- 归因留在句子里：谁说的，哪一天，哪个版本。
- 标题里的数字和"最好""替代""开源""免费"，逐个对照正文核对归因和适用条件。厂商的数字进标题时带上是谁说的（"官方称"），或者换成测试条件（"无并发读时"）。
- 影响判断的未核实信息，写在它影响的那句话旁边。抓取、清洗、检索的过程进交付说明，不占正文开头。
