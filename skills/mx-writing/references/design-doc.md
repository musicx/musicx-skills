# 设计文档和 PRD

写在动手之前、要别人评审或照着实现的东西读这一份：项目设计报告、技术方案、RFC、产品需求文档（PRD）。中英文通用。

这类文档有三种读者，要同时照顾：评审的人要判断方向对不对、取舍合不合理；实现的人要照着做，一句话不能有两种读法；半年后来查的人想知道当时为什么这么定。它和汇报的区别在于，读者会逐条读、逐条反对，写得含糊的地方会变成返工。

## 先判断要不要写、写多长

- 方案有悬念才值得写设计文档：有不止一种合理做法，选错了代价大，或者要跨团队达成一致。做法没有争议、文档只是把实现步骤抄一遍时，直接做，留一段说明就够。
- 小改动一到三页。大项目也控制在读者一次能读完的长度，细节给链接。
- PRD 写问题和要求，设计文档写怎么实现。两件事混在一篇里，评审的人分不清自己在批准需求还是在批准方案。

## 开头

第一段是摘要，评审的人只读这一段也知道该不该往下读：要做什么，为什么是现在，最大的一处取舍，需要评审者决定什么。文档头部写明状态（草稿、评审中、已定、已废弃）、作者和最后更新日期。

## 设计文档的骨架

用户或团队有模板就照模板。没有时用下面的默认骨架，没有内容的节整节删掉。

| 节 | 写什么 | 常见的毛病 |
|---|---|---|
| 背景与范围 | 读者不知道而又必须知道的现状，客观陈述，几段话 | 写成项目历史；在背景里夹带方案 |
| 目标与非目标 | 目标要能验证。非目标是"本来可以做、这次决定不做"的事，各带一句理由 | 非目标写成目标的反面（"不会崩溃"）；目标是一串形容词 |
| 方案 | 先给全貌（一张图或一段话），再分块讲。每个关键取舍写三样：选了什么，放弃了什么，换来了什么 | 贴整段代码、完整的接口定义或表结构（会过期，给链接）；只写"怎么做"不写"为什么这样做" |
| 考虑过的其他方案 | 认真考虑过的做法各写一段，说明它败在哪个条件上。"什么都不做"也算一个 | 摆一个一看就不行的方案来衬托 |
| 横切问题 | 安全、隐私、可观测、成本、迁移和回滚，只写这个设计确实碰到的 | 每项各写一句"已考虑" |
| 怎么验证 | 怎么知道做成了：指标、基线、验收条件；指标衡量什么、不衡量什么。分阶段上线时，写每一阶段的通过条件和出问题怎么退回去 | 只有上线日期，没有验收条件 |
| 风险与未决问题 | 已知的风险和应对；这个设计还缺哪些证据、打算怎么补；还没定的事，每件写明谁在什么时候之前定 | 未决问题没有负责人 |

## PRD 的骨架

| 节 | 写什么 |
|---|---|
| 问题与证据 | 谁，在什么场景下，遇到什么问题，多频繁、损失多大。证据写明来路：数据、访谈、工单，各有多少条 |
| 为什么是现在 | 不做会怎样，什么变了 |
| 目标与成功指标 | 每个指标带基线、目标值和观察期；要靠抽样判断的，写明样本量和怎样才算达标。上线了不等于成功 |
| 非目标 | 这一期不解决的问题、不服务的用户，各带理由 |
| 用户与场景 | 两三个具体场景，写用户原本怎么做、之后怎么做 |
| 需求 | 分优先级，逐条可验收（见下一节） |
| 约束与依赖 | 合规、兼容、性能、期限，依赖哪个团队的什么交付 |
| 未决问题 | 每件写明谁在什么时候之前定 |

PRD 里不写实现方案，除非某种实现本身就是约束（"必须复用现有的登录服务"）。

## 需求和约束怎么写

- **一条需求是一句可以检验的话：** 谁，在什么条件下，能做到什么，怎么算通过。`支持快速搜索` → `100 万条记录时，搜索结果的 P95 响应时间不超过 300 毫秒`。
- **义务等级全文一致。** "必须"是不满足就不能发布，"应该"是有正当理由可以不做，"可以"是允许但不要求。英文对应 MUST、SHOULD、MAY。改写时不能升降级。
- **优先级写出判据。** P0 是缺了它就不发布；P1 是这一期要做、但可以在发布后补；P2 是有余力再做。全是 P0 等于没有排。
- **写行为，不写实现。** `用 Redis 缓存结果` → `同一查询 5 分钟内重复出现时不再访问数据库`。
- **逐条编号**，评审时能说"R7 我不同意"。
- **数字带口径**：什么数据量、什么环境、哪个分位。素材里没有这个数时留 `[待填：……]`，不编一个看起来合理的。
- 指令类文字的歧义表在 `knowledge-doc.md`，需求和接口约定同样适用。

## 写法

- **决定和理由写在一起。** 一个决定后面紧跟它的理由和被否掉的选项。半年后有人想推翻它时，能看到当时已经考虑过什么。
- **事实、假设、决定分开。** 假设要标出来，并写明它不成立时哪一部分设计要改。
- **取舍明说代价。** "这样做会让写入延迟增加约 20 毫秒，换来的是不再需要对账任务"，不写"综合考虑后选择了方案 A"。收益、代价、没有变化的项和不适用的条件写在同一节。
- **小标题用短的主题词**，结论放在节的第一句。这类文档会被反复更新、按目录查找。
- **图用来讲结构和流程。** 图里的关键条件在正文里也要有，读者不该只能从图上读出约束。
- **不写成推销。** 评审的人在找问题，把已知的缺点自己先写出来，比被人指出来可信。
- **留带日期的修订记录。** 被推翻的决定标出来并写明原因，不删。实现偏离设计后，更新文档或在头部标"已过时"，错的设计文档比没有更糟。

## 交稿前

- 评审的人只读摘要和"考虑过的其他方案"，能不能判断方向？
- 实现的人拿到它，有没有哪条需求可以做成两种样子？
- 每个目标对得上一个验证办法吗？每条 P0 需求有验收条件吗？
- 非目标写了吗？未决问题有负责人和期限吗？
- 有没有只是在复述代码、读者去看仓库更准确的段落？
