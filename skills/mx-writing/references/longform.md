# 技术分享和面向公众的技术文章

读者自愿来读的技术长文读这一份：团队内的技术分享文档，公众号和博客文章，发到 X、Hacker News、Reddit 的技术文章，经验复盘，技术解读，评测，观点文。中英文通用。

和汇报相反，这里的读者没有义务读完，随时会走。所以除了讲清楚，还要多做两件事：让他愿意读下去，让他知道是谁在说话、凭什么说。这两件事都靠材料和判断，不靠修辞。

## 一、哪些必须来自作者

| 必须来自作者，助手不能代造 | 助手可以做 |
|---|---|
| 这篇文章的核心判断和切入角度 | 提三个候选主线供作者选；找支持和反对它的证据 |
| 亲历：做了什么、踩了什么坑、花了多少钱和时间 | 把作者讲的经过理顺、补上作者确认过的背景知识 |
| 态度：兴奋、后悔、不服气、没想明白 | 提结构建议，按定好的角度展开，核对事实，自查 |
| 最后的取舍：留什么、删什么、敢不敢下这个判断 | 指出哪一节缺材料、哪个判断没有依据 |
| 发出去之前亲自通读一遍 | 提醒作者这一步不能由助手代读 |

作者没给亲历，就不写亲历。说话的位置有四种：亲身做过、做过调查、熟悉这个行业、认真查完资料后形成了判断。四种都能写出好文章，但不能把后一种写成前一种。整理别人的内容时，标题和开头就说明是转述，来源不压到文末。

没有亲历时这样写：只抓最有把握的一两点，不包办整个问题；有可靠的流程材料时，选一个普通角色把过程走一遍，并明说这是常见情形；一段抽象解释之后尽快落到一次报价、一行配置、一次失败。不要把原因分成六七类、每类补一个限定、结尾再总结一遍，那样句句都对，读者却碰不到任何东西。

## 二、动笔前

**1. 这个题值不值得写。** 三个问题至少答上两个：读者读完能知道一件他原来不知道的事吗？有没有一个让人想看下去的问题或反差？有没有碰到读者自己正在经历的麻烦？只答得上一个，把这个判断告诉作者，不硬写。

**2. 定主线。** 观点文和经验文的主线是一个判断，不是一个话题："聊聊 Agent 的记忆"是话题；"给 Agent 加长期记忆，先坏掉的是检索，不是存储"是判断。好的判断有人会不同意，具体到能被验证。说不清时用这个句式逼一下：在什么条件下，A 通过什么机制改变了 B，结果是什么。机制讲解和教程的主线是读者的一个问题，加上他读完能判断什么或能做成什么："SQL 查询的各个子句按什么顺序生效，读完能判断一条查询合不合法"。

**3. 清点材料。** 一千二百字以上的文章，先列出至少五件有来路的材料：亲历的事、数字、原话、可以核实的公开出处、一次失败。类别名不算材料，同一个意思换种说法不算第二件，读者本来就猜得到的也不算。每一节要对得上至少一件。对不上就缩短篇幅，推理可以把材料连起来，不能自己繁殖出材料。要查资料才能写的，同时读 `research.md`。

**4. 读者默认是一个聪明、感兴趣、但不熟悉背景的同行。** 读者不是同行时，开头写明读这篇需要懂什么、不需要懂什么。

**5. 选一个原型。** 它决定文章怎么往前走。

| 原型 | 读者得到什么 | 怎么推进 |
|---|---|---|
| 踩坑、排查实录 | 我替你走了一遍 | 现象 → 当时相信什么、查了什么 → 哪条证据让判断变了 → 最后剩下的原因 → 还没解决的部分。没有可靠的调查记录时，只写复现、原因和修复，不补写没走过的弯路 |
| 实测、体验 | 跟我一起试 | 具体场景 → 逐个试，从最平常的到最出乎意料的 → 真实感受和对比 → 判断，以及它在什么条件下成立 |
| 基准、对比评测 | 一个可以查的结论 | 结论和排名 → 测的条件，指标衡量什么、不衡量什么 → 分项结果 → 局限。读者是来查结果的，不吊胃口 |
| 机制、原理讲解 | 一个能拿去判断的模型 | 一个读者认得出的困惑 → 最小的例子 → 模型 → 用它解释开头的困惑 → 这个模型能判断什么、不能判断什么 |
| 方法、经验分享 | 我自己在用的做法 | 每一节：判断 → 例子 → 具体怎么做 → 学习成本和容易失败的地方 |
| 方案、架构复盘 | 我们为什么这样做 | 先给结果和数字 → 再讲怎么做到的 → 取舍和没走通的路 → 别人能搬走的部分。没有数字时，写明为什么没有、打算怎么补 |

## 三、开头

- **从读者认得出的问题或一件具体的事开始。** 那次事故、那个 bug、一个带时间范围的结果数字、一条读者也写过的报错。不从定义、行业背景、"随着……的发展"开始，也不用假想的场景（"想象一下，凌晨三点……"）。读者是来查答案的，答案本身就是最短的开头。
- **读完前三段，读者要知道三件事：** 这篇讲什么问题，凭什么由你来讲，读下去能得到什么。
- **交代材料的来路。** 哪部分是亲手做的，哪部分是整理别人的，哪部分由 AI 执行、人只核对了哪几处。和所写的对象有利益关系（受雇、持股、赞助、推广链接）时说明。
- **可以给路线图，但要具体。** "先调阈值，再测校准，最后比成本"能帮读者决定读不读；"本文将从三个方面展开"不能。
- **可以用一张摘要卡开头：** 做了什么，最大的坑是什么，最值钱的收获是什么。五行以内。
- **开头最后再改一遍。** 全文写完后，用二十秒把这篇文章讲给一个人听，再和开头对照。对不上时，多半是文章在写的过程中变了，按写成的文章改开头。

## 四、怎么往前走

- **每写完一段问一句：读者现在最想知道什么？** 下一段就答这个。先讲发生了什么，他会问为什么；先给判断，他会问凭什么；先讲结果，他会问中间出了什么岔子。
- **抽掉中间一节，后面还接得上吗？** 接得上，说明这几节只是并列的要点。重排，让前一节的结论成为后一节的前提。一份可以任意调换顺序的清单撑不起一篇文章。
- **知识等问题走到那里再出现。** 读者问到钱再算钱，碰到那条限制再解释限制。例外：后面每一节都要用到的两三个前提，可以在前面集中交代。
- **用一个最小的例子把问题钉住。** 讲抽象的问题之前，先构造一个小到能心算的例子，让读者看见它确实会发生。一个例子用到底，比五个各用一次的例子省读者的力气。
- **数字后面写它推出的决定。** "误报率 3%，置信区间上界超过 5%，所以还不能宣布达标"，不停在数字上。
- **坑和失败写四样：** 什么条件下触发（带数字），原因或机制，怎么处置的，还剩什么没解决。每一步都顺利、每个数据都支持论点的文章，读者不信。
- **每个决定当场写代价。** 写收益时，旁边写代价和没有变化的项："错误率降了六成，训练时间变成四倍，推理延迟没变"。
- **给得出原件就给原件。** 完整的提示词、配置、命令、报错原文，比对它的描述有用。代码是真实跑过的片段，否则明说是示意。
- **至少下一个读者可能不同意的判断，并说出什么情况下你是错的。** "写入量在每秒一千次以下的，可以不看这一节。"推荐一种做法之后，紧跟它的例外。几个方案各写一段却不给结论，不算分析。
- **讲机制分三步：** 先用白话说出画面，再给术语，最后给工程事实（数字、复杂度、边界）。比喻删掉后读者对机制的理解毫无损失，它就是装饰。
- **岔出去要回来，回来要多带一样东西：** 一条证据、一个尺度或一个反例。出去一圈判断纹丝不动，这段只是在展示知识。
- **篇幅跟着材料走，不求对称。** 让你意外的那一节写五倍长，铺垫性的步骤一句带过。

## 五、声音

文章里始终有一个人，读者知道他站在哪里。

**人味从这些地方来：** 知识的来路（哪件事让我留意到这个问题，一开始怎么想错的，哪条材料改变了看法，哪一块到现在还没弄明白）；取舍（我为什么不选另一条路）；代价（花了多少，赔了什么）。每篇自然出现一两处就够，凑齐了又成了新模板。

**不从这些地方来：** 语气词和口头禅的数量，按篇幅分配的自嘲和吐槽，故意的不通顺，编出来的生活细节，拿资历顶替材料（"我测了一百多个小时"后面没有测试记录）。作者有自己的口头禅和句式时，写在风格说明里，照风格说明用。

- "我"用来讲亲历的事、交代证据在哪、下判断。不替读者说他是谁、他会怎么想。
- 姿态是同行对同行。作者原稿是"我跑过、我看到、我还没答案"的探索口气，就不要改成"我来告诉你该怎么做"的教程口气。
- 证据是一个项目的，结论就停在这个项目上。刚划完适用边界，不要又推到"你也可以"。

## 六、小标题、图表和数字

- 篇幅长、读者确实需要定位时才加小标题。小标题是一个判断或一个问题。按模块跳读的长复盘，一级小标题可以用主题词（"起因""出口方案"），判断放在二级小标题或节的第一句。
- 以段落为主。步骤、清单、多项对比才用列表和表格。手机上读，一段三五行，一段一件事。
- **图和表前面的那句引子自带结论。** 有的平台和抓取工具会丢掉图、表格和代码块，读者只剩这一句。图里的关键条件在正文里也要有。不为调节节奏凑图。
- **对比表之前先写怎么测的**，表里留一列写副作用或淘汰原因。
- **数字带条件：** 什么机器、什么版本、多大数据量、跑了几次。自己测的、别人报告的、估算出来的分开写；估算的写明怎么估的。口径变了的两组数标明不可比。容易过期的事实（价格、版本、界面位置）带日期。
- 没有比较、没有查的部分，写明没做以及原因。

## 七、结尾

停在这几种之一：一个具体的建议或下一步；一个你确实还没有答案的问题；一个因此改变了的决定，或者付出的代价；操作类文章可以停在一份动作清单上，每条带适用条件，不出现正文里没有的新论断；写明前提的外推（"如果这三条在十年后仍然成立，那么……"），每一条对得上前文的一项实测。

不停在：把全文升华一遍、时代和人生、没有前提的展望、一句可以做成卡片的话、索取互动（"欢迎留言""收藏这篇""关注我"、导流的附言）、推销。作者素材里有他自己的感悟，原样保留；素材里没有的感悟不替他写。回到开头那件事是可以的，只在它带回了读者现在才看得懂的含义时用。拿不准时，比你想停的地方早一步停。

## 八、标题

- 给四到五个候选让作者挑：两三个带具体信息的，一两个平铺直叙的。无法询问时，用平铺直叙里最具体的那个。
- 具体胜过抽象（"150 行"胜过"一份文档"），说人话，三十个字以内，前几个字就要有信息。对象名本身就能当标题（"ARCHITECTURE.md""机械表"），只要正文回答的问题清楚。
- 正文必须兑现标题。不用"史上最全""保姆级""一文读懂""唯一指南"，不用"浅谈""探索与实践"。"所有人都做错了"这类翻案标题，只有正文真的用材料推翻了才用。
- 不在钩子上花力气。这套规程参考的语料里，同一位作者的文章，标题带不带数字、问句、夸张词，和收藏率、点赞率看不出关系（见 `sources.md`）。力气花在读者能拿去用的东西上。
- 遮住正文，只看标题，一个陌生人能不能说出这篇大概讲什么？

## 九、发到哪里

- **Hacker News：** 投稿标题用文章原题，不加评价、感叹号、全大写和凑数的数字前缀；投原始出处。Show HN 只用于读者能亲手试的东西，博客文章按普通投稿。社区规则不接受生成的或经 AI 改写的帖子和评论，这部分由作者自己写。（依据其投稿规范，2026-11 读取。）
- **Reddit：** 各版的自荐和链接规则不同，发之前读那一版的规则。
- **会被抓取、转载的文章（X 长文、博客）：** 经过抓取后，加粗、表格和图常常丢失，关键结论放在句子里。
- **公众号：** 手机上读，段落更短，外链点不开时把关键出处写进正文。

## 十、改长稿

- **先画地图，再改句子。** 通读后列出每一节一句话在说什么，标出三类问题：同一个判断或清单在两节以上各写了一遍；正文在复述紧邻的表格；整节对主线没有贡献。不要一遍把整篇重写，那样会盖掉作者亲手调过的句子，也没法逐处核对。
- **作者自己的成稿：** 删节、合并、调顺序先提出来等确认；句子只动病句、错字和明显的机器腔；交回时附上每一处删改，作者可以逐条否决。无法询问时只做句子层的修改，结构建议写在交付说明里。
- **改完对照原稿查四样东西有没有丢：** 作者原本的反应被换成了四平八稳的抽象词；前后呼应的一组说法断了一环；带理由的句子被砍成了光秃秃的结论；具体的数字和名字被抹成了"很多""某工具"。丢了就恢复原文。更短、更克制不等于改好了。

## 十一、发出去之前和之后

1. 这篇是谁在说？他手里最硬的三样材料是什么，在文中哪里？
2. 换一个作者，能不能写出差不多的一篇？能，就是缺独有的材料或判断。这要回去找作者补，改词解决不了。
3. 读完之后，读者多了哪一种判断能力，或者能做成哪一步？用一句话说得出"这篇能帮谁解决什么"吗？
4. 从头读一遍，在哪里走了神、哪里要回头找主语？那里就是要改的地方。
5. 有没有未经授权的内部信息？有没有拿同行做反衬？
6. 发出去之后发现有错或判断被推翻：在原处加带日期的更正，写明原来怎么写的、怎么发现的、改成了什么，不悄悄改掉。
